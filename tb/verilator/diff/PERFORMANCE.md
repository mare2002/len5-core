# Differential verification performance

Measurements on 2026-10-12. The dominant cost is **RTL observation through VPI**,
including hierarchy strings, metadata lookup and repeated register-file reads.
Spike execution is a small part of this workload. No verification comparisons,
commit/flush handling, store authorization, or unsupported-instruction checks
were removed.

## Execution flow and where time goes

1. Make/FuseSoC validate cached Spike libraries, fingerprint sources/options,
   elaborate Verilator/XML when necessary, generate `diff_layout.hh`, compile,
   and link the executable. Builds are separate from the runtime measurements.
2. The testbench initializes the RTL and the monitor. Spike independently loads
   the same HEX into sparse byte memory and synchronizes the selected reset CSRs.
3. Before a rising edge, the monitor reads the settled RTL through VPI. It
   processes the old commit register, captures load requests before flushes,
   handles backend/frontend squash separately, and observes dispatch, execution,
   memory and accepted fetch handshakes. Accepted fetches associate with the next
   architectural reference order. `processor_t::step(1)` supplies an independent
   reference record when needed; retained records support refetch after flush.
4. `dut->eval()` advances RTL. After a rising edge, complete architectural-prefix
   checkpoints compare actual integer/FP registers and selected CSRs. Out-of-order
   commits delay the checkpoint until the prefix catches up to the newest commit.
5. Before a falling edge, the checker validates irreversible external stores at
   the emulator's actual write boundary, including authorization and memory order.
6. On exit, the checker validates completion and writes `report.json`. When waves
   are enabled it also journals comparison events and merges them with the original
   FST. Annotation time is included in the end-to-end wall-clock measurements.

The checker calls Spike and its C++ methods directly. The observation boundary is
VPI, not a per-instruction SystemVerilog DPI call. There is no measured Spike/DPI
round-trip bottleneck to eliminate. Text instruction traces and FSTs are separate
options. Simulation targets default both on; benchmark/optimized targets default
both off.

## Method

Host: Intel Core i7-1165G7, Fedora Linux, GCC 16, Verilator 5.040, pinned Spike
v1.1.0 with commit logging compiled in and textual Spike printing disabled.
The original build uses `-Os` for Verilator fast/global objects; the final checked
build uses `-O2`. Neither disables assertions or enables fast-math.

`benchmark-diff.py` times the entire executable with `time.perf_counter()`, captures
console logs, hashes the binary and firmware, and checks exit status, full JSON
reports and RTL cycle counts against the baseline. Throughput is the testbench's
reported **CPU cycles / wall seconds**; checked instruction throughput uses the
checker's committed count. These differ from the testbench's retired count because
its statistics cover a different counting interval.

Final waves-off measurements use five serial repetitions per variant/workload,
rotating variant order between repetitions. No compilation runs concurrently with
these measurements. Medians and ranges are reported; no CPU affinity or frequency
lock was applied. Firmware is identical between variants; Embench was compiled
with `SPIKE_CHECK` to omit unsupported timing CSRs, retaining its result checks.

Initial exploration reused the supplied cached executable. A full rebuild changed
its exit boundary by one cycle, so those exploratory timings are excluded from the
final comparison. Final baseline binaries compile the original checker sources
against the same freshly generated RTL source as the optimized builds; final
reports and cycle counts match exactly.

Component timing uses temporary instrumented copies, generated by
`profile-diff.py`. Timers are inclusive: Spike is included in checker calls;
checker calls and signal reads are included in monitor callbacks. They must not be
summed as disjoint categories. Per-read clocks add overhead; speedup claims use
uninstrumented binaries. Gprof sampling was used as an initial cross-check, not
as an exact decomposition of library/allocation costs. Linux perf and Valgrind
were unavailable. A temporary glibc allocation interposer counted allocations
separately from the timed benchmarks.

### Component profile, `st`, waves off

Seconds in one instrumented run per build; see the inclusive-timing caveat above.

| Component | Original | Optimized execution |
| --- | ---: | ---: |
| Before-rising monitor, including its checker calls | 1.877 | 0.593 |
| After-rising monitor, including checkpoint comparisons | 1.401 | 0.209 |
| Before-falling monitor | 0.026 | 0.011 |
| RTL `eval()` | 0.420 | 0.386 |
| Signal-read implementation, nested in the monitor | 2.653 | 0.601 |
| Public checker calls, including Spike | 0.094 | 0.070 |
| Spike reference step, nested in checker calls | 0.023 | 0.022 |
| Monitor/Spike initialization | 0.0022 | 0.0020 |

Originally the monitor accounted for about **89%** of timed monitor-plus-eval work.
Spike's 27,576 steps took only 23 ms; step batching cannot recover the seconds
spent observing RTL. The six-step difference versus checked commits is reference
lookahead, not an unbounded repeated-PC search. The ordered live-window maps,
register/CSR snapshots and memory bookkeeping are measurable but secondary.

Signal reads fell from **5,575,723 to 4,441,233**: exactly 1,134,490 unnecessary
reads removed by the 70-register/CSR sampling guard on 16,207 ineligible edges.
All 18,715 real checkpoints remain. The temporary allocation interposer counted
**24,114,835 → 9,870,201 allocation calls** (59.1% fewer), with cumulative requested
bytes **1.841 GB → 0.880 GB**. These are allocation churn, not peak resident memory.
The remaining pinned Verilator VPI implementation still computes `fullname()`
inside `vl_vpi_get_value()` on every read; cacheable monitor metadata is not the
only source of string work.

Profiles: `fresh-baseline-profile/st/0/console.log` and
`final-profile/off/0/console.log` under `build/performance/`. Allocation sources
and raw counters are retained there as `allocations.c` and `allocations/`.

### Logging and waveforms

Three runs per output mode on `st`; medians include FST finalization/annotation.

| Mode | Original seconds | Optimized seconds | Interpretation |
| --- | ---: | ---: | --- |
| Same checked executable without `--diff`, no output | 0.352 | 0.328 | Diagnostic RTL-only floor, **not** a verified run or an ordinary non-VPI build |
| Checking plus committed text trace, no waves | 3.736 | 1.133 | About 0.037 s above the optimized no-output median; text logging is secondary here |
| Checking plus original and annotated FST, no text trace | 20.246 | 10.183 | **1.99×** overall speedup; final throughput 3,424 CPU cycles/s |

With the execution optimizations but the original annotation loop, the waves-on
median was 13.125 s (range 13.111–13.327). Caching the immutable per-lane annotation
handles reduced that to **10.183 s** (range 10.085–10.236), a further **22.4%**
reduction. No annotation fields or events were removed. Final native-build smoke runs of all
four workloads also matched the baseline after the annotation change.

Before that final cache, an instrumented waves-on run spent **9.165 s** in
finish/annotation and **2.283 s** in live FST dumping; checker calls including
journaling took **0.333 s**. Thus disk journaling alone was not the main output
bottleneck: repeated handle lookup and FST processing dominated. The `st` journal
contains **1,966,581 events** (about 181 MiB), alongside approximately 24 MiB of
original FST and 37 MiB of annotated FST.

After handle caching, the corresponding instrumented finish/annotation time was
**6.226 s**; live dumping was **2.341 s** and checker calls including journaling
were **0.364 s**. The remaining waves-on cost is primarily FST processing/output.
The profiling log is `build/performance/annotation-profile/waves/0/console.log`.

Three warm `make verilator-build-debug` cache checks took 0.285, 0.264 and 0.261 s,
without recompilation. This orchestration cost is excluded from the executable
benchmarks and matters especially for short programs such as `load_store`.



## Implemented changes and correctness

* `checkpoint_due()` exposes the existing eligibility predicate. The monitor
  checks it before reading 31 integer registers, 32 FP registers and seven CSRs.
  `checkpoint()` retains the same guard. Every eligible checkpoint still observes
  the actual post-edge RTL state and compares every original field.
* Vector extraction processes at most three masked 32-bit words rather than up
  to 64 individual bits. It retains the `bval` unknown-bit check within exactly
  the requested field, including unaligned 64-bit fields.
* Signal groups own stable bindings to generated layouts, fields and VPI handles.
  Full hierarchy strings and XML lookups are resolved on first use. Short lookup
  keys use views into owned, stable strings. Each observation still calls
  `vpi_get_value`; no RTL values are cached across phases or cycles. Width, field,
  array-bound and unknown-bit errors remain checked. Per-cycle copies of two
  immutable layout maps were also removed.
* Annotation resolves common and field-specific output handles once per lane.
  The hierarchy, signal creation order, emitted values, pulses, retrospective
  confirmations and two-pass streaming journal processing are preserved.
* Checked builds use `OPT_FAST=-O2` and `OPT_GLOBAL=-O2`. Spike's existing compiler
  settings, RTL functionality, assertions, wave support and all checker options
  remain available.

Instruction identity is still based on dynamic order, never a PC search. No
reference records, checkpoints or instruction classes are skipped. Active ROB
ownership, committed records, load-response tombstones, store lifetimes, tentative
versus confirmed mismatches, and frontend/backend recovery remain unchanged.

## Ranked follow-up opportunities

| Priority | Optimization | Expected impact | Complexity | Correctness risk |
| --- | --- | --- | --- | --- |
| 1, implemented | Cache signal metadata/path construction | Largest measured source-level improvement | Medium | Low: retain fresh VPI reads and validation |
| 2, implemented | Compile fast/global simulation code with `-O2` | 33.2% incremental waves-off reduction on `st` | Low | Low: no relaxed arithmetic or disabled assertions |
| 3, implemented | Cache per-lane annotation handles | 22.4% additional reduction in waves-on wall time | Low/medium | Low: full decoded waveform comparison |
| 4, implemented | Gate register sampling by exact checkpoint eligibility | Workload-dependent; most useful during stalls/incomplete prefixes | Low | Low: shared predicate, same post-edge checkpoint |
| 5, implemented | Extract vector fields a word at a time | Smaller measured improvement | Low | Low: all tested alignments/widths and unknown-bit locations |
| 6 | Read each packed VPI signal once per observation phase, or generate typed read-only accessors | Potentially substantial fraction of remaining observation time; not measured | Medium/high | Medium: invalidate at every eval/edge, preserve old-commit versus post-edge sampling and layout checks |
| 7 | Fixed storage for selected CSR snapshots; avoid constructing successful unjournaled event payloads | Small on measured waves-off workloads | Low/medium | Low/medium: retain discrepancy serials, full CSR coverage and waveform events |
| 8 | Change instruction containers/pruning or sparse reference memory | Low priority given measured checker/Spike cost; could matter on other workloads | Medium | Medium: preserve response tombstones, byte initialization and self-modifying-code detection |
| 9 | Batch Spike execution while retaining per-instruction hooks and snapshots | Very limited upside on these profiles | High | High: must retain every intermediate operand, log and snapshot; not implemented |

For throughput runs where waveforms/text traces are not needed, explicitly select
`DUMP_WAVES=false DUMP_TRACE=false`, as benchmark targets already do. All checking
continues. Waveform-enabled timings above quantify the output cost; annotation
and logging functionality have not been removed or silently disabled.

## Validation

* Native FuseSoC/Verilator checked build and incremental C++ builds succeeded.
* Five interleaved repetitions of each measured variant/workload matched full
  baseline reports and cycle counts. `st` retained 27,570 commits, 18,715
  checkpoints, 8,855 out-of-order commits, 6,856 squashes, 419 frontend recoveries,
  no pending stores and the same one pending terminal next-PC comparison.
* All four directed observation faults (`operand`, `cdb`, `register`, `store`)
  still fail with status 1. A directed workload begins with an instruction that
  actually consumes rs1: the existing one-shot operand injector can otherwise be
  consumed by an instruction without a checked source operand.
* FP load/store and FADD.D probes pass; FLW still exposes the NaN-boxing mismatch
  with status 1; an unsupported counter-CSR probe still exits with status 2.
  Baseline and final reports, mismatch/confirmation timestamps, event journals,
  and committed text traces match exactly for all eight cases.
* Decoded annotated waveform streams match for all eight cases. The full `st`
  comparison also matches across **80,542,703 VCD lines**, excluding only the
  creation-date block. Its SHA-256 is
  `7fa7b55ad80cb3eaa8098c0f7b4445175cc73675cd02194387e5714bfca7c117`.
  This checks the actual annotated signal histories, beyond report equality.
* The standalone C++ test compares vector extraction with an independent
  bit-at-a-time oracle across every width 0–64, offsets 0–63, and each possible
  unknown-bit location in the 128-bit test vector. It also checks checkpoint
  eligibility through out-of-order commits, duplicate sampling, squash/ROB reuse,
  and a deliberately corrupted checkpoint.
* `git diff --check` and Python syntax checks pass. GCC ASan/UBSan links were
  attempted, but their runtime libraries are missing from this host; the tests
  passed without sanitizers. The repository-wide `make check`/full ISA compliance
  suite was not run. These results establish the tested behavior, not exhaustive
  correctness of every possible instruction stream.

The temporary correctness tests, directed probes, test runners and their artifacts
were removed at the user's request. The results above record the validation
performed before removal.


## Reproduce

Build once using the normal checked target, then time the executable independently
of FuseSoC startup/build-cache checks. Use firmware produced by
`make run-debug BENCHMARK=st`, which automatically adds `-DSPIKE_CHECK`:

```sh
make verilator-build-debug VERILATOR=/path/to/verilator-5.040/bin/verilator \
    FUSESOC=/path/to/fusesoc JOBS=4
python3 scripts/sim/benchmark-diff.py \
    build/debug/sim-diff-verilator/Vtb_bare build/embench_debug/run/st/main.hex \
    build/performance/my-run --repeats 5
# Add --reference <baseline>/summary.json to require identical verification results.
# Add --waves and/or --trace to measure those modes explicitly.
```

To profile an already-built model, make separate timed copies of four C++ files
and link against the existing generated model and Spike objects. Do not compile
other variants into that model directory concurrently. The helper reads optimization
options from Edalize's `config.mk`, so the objects must match that configuration.

```sh
python3 scripts/sim/profile-diff.py build/performance/profile
python3 scripts/sim/benchmark-diff.py \
    build/performance/profile/Vtb_bare build/embench_debug/run/st/main.hex \
    build/performance/profile/run --repeats 1
# PROFILE lines appear in run/0/console.log, in seconds with invocation counts.
```

Benchmark binaries, source snapshots, command lines, logs, reports and timing
samples are retained under `build/performance/` (ignored by Git).
